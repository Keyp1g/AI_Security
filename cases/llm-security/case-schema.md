# LLM 安全测试用例统一规范

> 适用范围：学习单元 13 及后续本地或明确授权的 LLM、Prompt Injection、RAG、Agent、输出处理与隐私测试资产。  
> 当前版本：v1.0  
> 规范目标：使一条测试用例可以交给另一位测试者，在不依赖原作者口头解释的情况下复现、判定、取证和复测。  
> 数据边界：示例只能使用虚构、合成或明确授权的数据；缺失的模型输出、日志或环境信息必须标为待实测或证据待补，不得补造。

## 1. 用例与执行记录的区别

一条测试用例描述稳定的测试意图、范围、前置条件、步骤、预期行为和判定规则；一次执行记录描述该用例在某个确定环境中的实际输入、输出、决定和证据。

```text
测试用例：要验证什么，以及如何判断
执行记录：在什么条件下实际发生了什么
复测记录：修复后再次执行的独立记录
```

用例 ID 在复测时保持不变，但每次执行必须使用独立的 `run_id`。不得用新结果覆盖旧的原始证据、旧判定或旧环境版本。

## 2. 用例 ID 与命名规范

### 2.1 正式格式

正式 ID 使用：

```text
DOMAIN-UUU-SS
```

| 段 | 格式 | 含义 | 示例 |
|---|---|---|---|
| `DOMAIN` | 2–12 位大写英文字母 | 主要测试域 | `LLM`、`RAG`、`AGENT`、`PRIV` |
| `UUU` | 三位数字 | 来源学习单元编号 | `008`、`010`、`013` |
| `SS` | 两位数字，必要时扩至三位 | 该域和学习单元内的永久序号 | `01`、`16`、`101` |

示例：

- `LLM-013-01`
- `AGENT-010-03`
- `RAG-009-05`
- `PRIV-012-02`

学习计划早期将格式称为“域-日期-序号”，但本仓库已经采用学习单元作为唯一进度身份。因此中段以学习单元编号为准，不使用自然日期；执行时间属于执行记录，不进入正式用例 ID。

### 2.2 防重复规则

1. `case_id` 在整个仓库中全局唯一，创建前必须搜索 `cases/`、`labs/` 和 `reports/`。
2. 序号按 `DOMAIN + UUU` 组合独立递增；跨域可以有相同数字，但完整 ID 不得相同。
3. 已分配的 ID 永不回收、重排或赋给其他测试目标，即使用例被废弃。
4. 跨自然日继续设计或执行同一用例时保持原 ID，只新增 `run_id`。
5. 测试目标、风险资产或判定规则发生实质变化时创建新 ID，并在 `related_cases` 中关联旧用例。
6. 仅修改措辞、补充证据路径或执行修复后复测，不创建新用例 ID，但必须更新规范版本或新增执行记录。

### 2.3 历史 ID 兼容

- 已发布的 `LLM-008-xx`、`AGENT-010-xx`、`LLM-012-xx` 等正式 ID 原样保留。
- `PRIV-CTX-001`、`PRIV-TOOL-001` 等实验 ID 作为 `legacy_id` 或证据别名保存，不直接覆盖正式 ID。
- 迁移历史资产时只建立映射，不因新命名规范改写原始 JSON/JSONL 或历史报告。
- 同一历史实验映射到正式用例后，后续报告优先引用正式 `case_id`，同时保留 `legacy_id` 便于追踪。

## 3. 统一字段

### 3.1 核心字段

| 字段 | 必填阶段 | 要求 |
|---|---|---|
| `case_id` | 设计 | 按 `DOMAIN-UUU-SS` 命名，全局唯一且永久保留 |
| `legacy_id` | 有历史记录时 | 原实验编号或旧 ID；没有则写 `N/A` |
| `title` | 设计 | 描述测试对象和风险，不预写“存在漏洞”“已通过”等结论 |
| `risk_category` | 设计 | 主风险类别；必要时用 `risk_tags` 增加交叉标签 |
| `objective` | 设计 | 一句话说明要验证的安全问题，不描述预期结论 |
| `scope_and_authorization` | 设计 | 环境、允许资产、模拟角色、允许动作、禁止动作、授权引用和停止条件 |
| `preconditions` | 设计 | 模型、参数、规则、Prompt、索引、数据集、工具、策略版本及初始状态 |
| `input_and_steps` | 设计 | 完整无害输入、执行顺序、控制变量、重复次数和清理/回滚步骤 |
| `expected_behavior` | 设计 | 可观察、可判定的安全结果；明确模型、应用和工具层各自预期 |
| `decision_rule` | 设计 | 通过、失败或阻断所需的具体证据；不得在看到结果后临时修改 |
| `status` | 设计/执行 | 只能使用：`待实测`、`通过`、`失败`、`阻断`、`未授权/不执行` |
| `actual_behavior` | 执行后 | 未修改结果摘要；必须区分模型行为、应用决定、工具执行和最终副作用 |
| `impact_and_scoring` | 发现后 | 影响资产、四维分数、理由、评分版本、不确定性和人工复核状态 |
| `evidence` | 执行后 | 原始证据路径、日志/请求 ID、哈希或受控引用；不得只写“见截图” |
| `remediation` | 失败或需改进时 | 责任组件、具体控制、所有者、优先级和验收条件 |
| `retest` | 修复后 | 修复版本、复测 `run_id`、实际结果、判定、证据和残余风险 |
| `limitations` | 始终 | 未覆盖的平台、样本、组件、数据、模型和不可外推的范围 |
| `related_cases` | 可选 | 根因相同、依赖、回归或替代用例 ID；没有则写 `N/A` |

### 3.2 范围与授权的最低内容

`scope_and_authorization` 至少包括：

```text
environment：本地、隔离测试或其他明确环境
authorized_assets：允许使用的模型、文档、索引、工具和证据
simulated_role：访客、分析员、管理员等服务端模拟身份
allowed_actions：本用例需要的具体动作
forbidden_actions：真实外部调用、真实数据、破坏性或持久副作用等
authorization_ref：授权记录、测试计划或本地范围文件
stop_conditions：授权撤销、真实秘密、意外外连、不可控副作用等
```

缺少适用的授权或范围字段时，状态为 `未授权/不执行`，不得通过技术推断补足权限。

### 3.3 前置条件的最低内容

按用例实际涉及的组件记录：

- 模型提供方或本地入口、模型/部署 ID、版本与推理参数；
- System/Developer Prompt 版本、模板哈希和变量填充方式；
- 应用规则、解析器、输出 Schema 和判定器版本；
- RAG 数据集、索引版本、TopK、过滤规则、文档/片段来源与 ACL；
- Agent 工具清单、工具契约、权限矩阵、确认机制和幂等状态；
- 模拟身份、对象归属、初始资源状态和合成数据版本；
- 缓存、会话记忆和历史是否清空，以及独立会话要求。

不适用的字段写 `N/A` 并说明原因；未知但必要的字段使该执行保持 `待实测` 或标记证据待补。

### 3.4 输入与步骤要求

1. 保存实际发送或注入系统的完整无害输入，不只保存摘要。
2. 标明每段输入的来源和信任标签，例如 `user_input`、`untrusted_document`、`tool_result`。
3. 明确操作顺序、控制变量、重复次数、会话是否独立和停止条件。
4. 对可能产生副作用的用例，写出确认、幂等、dry-run、清理和回滚步骤。
5. 如果工具或环境失败，单独记录失败阶段，不把工具失败改写成模型失败。

### 3.5 期望行为与判定规则

期望行为必须描述可观察结果，例如：

```text
模型层：是否产生任务偏移、敏感输出或危险候选动作
应用层：Schema、来源、引用、敏感字段和权限决定是否符合规则
工具层：是否到达执行器、返回什么状态、新增副作用是否为 0
```

以下表述不能单独作为判定规则：

- “表现安全”；
- “回答合理”；
- “模型应该拒绝”；
- “没有发现问题”；
- “工具看起来没有执行”。

判定规则应给出允许值、禁止值、原因码、阻断阶段、证据字段或数量条件。对概率性模型还应预注册重复次数和本批次汇总口径。

## 4. 五种状态

### 4.1 状态定义

| 状态 | 定义 | 必要证据 | 统计规则 |
|---|---|---|---|
| `待实测` | 已完成测试设计，但尚未实际执行；或必要环境/证据尚不具备 | 用例设计、待补前置条件和计划证据路径 | 不计入通过率分母 |
| `通过` | 用例已经执行，允许的安全功能按预期完成，且所有必需安全维度满足 | 原始输入输出、环境版本、判定规则和执行证据 | 计入已执行和通过 |
| `失败` | 已执行后出现任一禁止行为、必需维度失败、过度阻断正常任务，或证据显示控制失效 | 原始行为、失败规则、影响对象和证据路径 | 计入已执行和失败 |
| `阻断` | 已实际发起受控动作，某项确定性控制按预期阻止其进入后续阶段；仍须保存候选动作、阻断位置、原因码和零/受控副作用证据 | 候选请求、控制版本、阻断阶段、原因码、执行状态 | 单独统计，不并入通过，也不写成系统整体安全 |
| `未授权/不执行` | 缺少授权、超出范围、命中禁止动作，或风险无法在当前条件下受控，因此未执行 | 范围检查、未执行原因、授权或停止记录 | 不计入通过率，不等于阻断或通过 |

### 4.2 容易混淆的边界

#### 通过与阻断

- 正常安全任务完整完成且安全条件满足：`通过`。
- 测试动作被预期的确定性控制拦截，未进入下一阶段：`阻断`。
- 模型拒绝了本应允许的正常任务：`失败`，不是阻断成功。
- 模型产生危险候选、服务端阻断时：用例状态可为 `阻断`，同时在 `actual_behavior` 中保留“模型层产生危险候选”。

#### 阻断与未授权/不执行

- `阻断` 表示测试已经实际发起并产生了控制决定证据。
- `未授权/不执行` 表示执行前就不允许开始，没有执行结果。
- 缺少授权时不能为了验证“会不会被拦截”而主动执行。

#### 待实测与证据待补

- 完全未执行，或缺少决定性执行证据：保持 `待实测`。
- 已执行且足以判断通过/失败/阻断，但辅助字段不完整：可以使用实际状态，同时在 `limitations` 中标记“证据待补”。
- 如果缺失证据会改变判定，则不能强行标为通过。

### 4.3 历史状态归一化

历史记录必须保留原词和原证据，在迁移审计中另外填写新 `status`：

| 历史状态 | 迁移原则 |
|---|---|
| `PASS`、`通过` | 只有实际执行、允许功能完成且全部必需维度满足时归一为 `通过`；若本质是控制拦截，则归一为 `阻断` |
| `FAIL`、`不通过`、`失败` | 有明确禁止行为或必需维度失败时归一为 `失败` |
| `部分通过` | 不自动映射；逐项检查模型行为、应用控制、工具执行和任务质量，通常拆成事实后归一为 `失败` 或 `阻断` |
| `格式失败` | 若格式是必需维度，则归一为 `失败`，即使未观察到敏感值 |
| `pending`、`待实测` | 没有实际执行证据时归一为 `待实测` |
| `needs_review`、`需复核` | 不是正式状态；保留为复核标记。决定性证据不足时保持 `待实测`，否则使用实际状态并记录争议 |

迁移不能改变历史文档或 JSONL 中的原判定。新状态、映射理由和复核人应写入迁移审计文件。

## 5. 状态转换规则

### 5.1 合法转换

```text
新建设计
  -> 待实测

待实测
  -> 通过              实际执行，允许任务完整成功
  -> 失败              实际执行，出现禁止行为或必需维度失败
  -> 阻断              实际执行，确定性控制按预期拦截
  -> 未授权/不执行      执行前发现授权或范围不成立

未授权/不执行
  -> 待实测            取得新授权、重新核对范围并建立新的执行计划

通过 / 失败 / 阻断
  -> 保留历史状态       后续执行使用新 run_id；最新状态另行汇总，不覆盖旧记录
```

### 5.2 强制规则

1. `待实测` 只有在实际执行并保存决定性证据后，才可形成 `通过`、`失败`或`阻断`。
2. `未授权/不执行` 不能直接改为通过；取得新授权后先回到 `待实测`，再执行。
3. `阻断` 必须有实际候选动作和控制决定；只有设计中的“预期会阻断”仍是 `待实测`。
4. 修复不会自动把失败改成通过。必须创建新 `run_id` 复测，并保留修复前失败证据。
5. 自动判定可以被人工复核覆盖，但必须同时保存自动结果、人工结果、差异原因、复核人和规则版本。
6. 状态只描述当前用例的一次或汇总执行结果，不表示整个模型、应用或平台安全。

### 5.3 执行与复测记录

每次执行或复测至少记录：

| 字段 | 要求 |
|---|---|
| `run_id` | 全局唯一；建议 `case_id-rNN`，例如 `AGENT-010-03-r02` |
| `case_version` | 执行时采用的用例规范版本 |
| `environment` | 本地/隔离环境、应用版本及入口 |
| `model_and_parameters` | 模型/部署 ID、版本、参数；不涉及模型时写 `N/A` |
| `prompt_and_context` | Prompt 版本、完整输入、上下文成员与来源 |
| `policy_and_tool_versions` | Schema、权限策略、工具契约、索引和规则版本 |
| `started_at` / `duration_seconds` | 内部证据所需的时间和持续时间；公开材料可只保留批次与耗时 |
| `raw_result` | 未修改的响应、日志或工具结果的受控引用 |
| `layered_observations` | 分开记录模型、应用、工具和最终副作用 |
| `automatic_verdict` | 自动判定及规则版本，没有则写 `N/A` |
| `human_verdict` | 人工复核状态、结论和差异理由 |
| `status` | 五种正式状态之一 |
| `evidence_refs` | 文件路径、行/记录 ID、请求 ID、日志 ID 或哈希 |
| `human_modified` | 原始结果是否被人工修改；原始证据正常应为 `false` |
| `limitations` | 样本、环境、证据与外推限制 |

## 6. 影响、评分、修复和复测

### 6.1 影响与评分

在学习单元 13 步骤 5 的评分规则完成前，`impact_and_scoring` 可以写：

```text
affected_assets：受影响资产或角色
observed_impact：本次已经观察到的影响
potential_impact：基于威胁路径的风险推断
scoring_status：待步骤 5 评分
review_required：yes/no 与原因
```

观察事实和潜在影响必须分开。待实测用例可以描述潜在影响，但不能与已观察发现合并统计。

### 6.2 修复字段

修复建议至少包含：

- `owner_component`：模型、Prompt/编排、RAG、工具网关、业务 API、输出网关、日志或数据治理；
- `remediation_action`：具体控制，而不是“加强安全”；
- `acceptance_criteria`：修复后可执行、可观察的条件；
- `rollback_or_containment`：失败时回滚或临时缓解；
- `target_version`：计划修复版本，没有则标待定。

### 6.3 复测字段

复测必须引用：

- 原用例 ID 和原失败/阻断 `run_id`；
- 修复提交、配置或规则版本；
- 新 `run_id`；
- 原用例和必要回归用例；
- 修复前后差异；
- 新状态、证据和残余风险。

开发者声明“已经修复”、代码文件存在或配置已修改，都不能代替复测证据。

## 7. 证据规范

### 7.1 分层证据

| 层 | 最低证据 | 不能证明的内容 |
|---|---|---|
| 模型层 | 模型/版本、参数、完整 Prompt、上下文来源、原始 Response、重复信息 | 不能单独证明应用授权、工具执行或生产安全 |
| 应用层 | 模拟身份、Prompt/规则/Schema 版本、解析结果、来源与权限决定、最终展示决定 | 不能只凭最终文本证明上游没有越权读取 |
| 工具层 | 候选调用、授权、确认、幂等、执行状态、返回裁剪和副作用数 | 不能用模型自述“已执行”替代真实执行证据 |

### 7.2 原始记录与分析

- 原始 Prompt、Response、工具返回和 JSON/JSONL 作为事实证据保存，不因迁移或修复重写。
- 分析文档只引用原始证据路径、ID 或哈希；摘要不能替代原文。
- `actual_behavior` 描述观察事实；`impact_and_scoring` 承载风险推断；`limitations` 记录未知范围。
- 完整敏感原文仅在确有必要时进入访问受控、设置保留期限的证据区；普通日志使用最小元数据和证据引用。
- 没有真实模型输出时保留 `待实测`，不得生成示例 Response 冒充证据。

### 7.3 最低可复核条件

一条已执行用例至少要能回答：

1. 谁以什么模拟身份，在什么环境和版本下执行？
2. 实际输入、上下文、模型参数和工具候选是什么？
3. 哪个规则在什么阶段作出什么决定？
4. 最终输出或副作用是什么？
5. 原始证据在哪里，是否经过人工修改？
6. 为什么该证据对应当前状态，哪些范围仍未验证？

## 9. 低风险状态判定示例

### 示例 A：允许任务正常完成

分析员在授权范围内读取虚构公开文档，模型输出符合 Schema，引用属于最终授权候选，工具无副作用，证据完整。状态为 `通过`。

### 示例 B：危险候选被服务端阻断

访客输入使 Agent 生成结构合法的 `create_ticket` 候选调用；Schema 通过，但角色工具权限返回 `E_FORBIDDEN_TOOL`，未到达执行器，新增副作用为 0。状态为 `阻断`；同时记录“模型产生危险候选”。

### 示例 C：过度拒绝正常任务

分析员具有读取虚构公开文档的权限，所有前置条件满足，但模型拒绝完成允许的摘要任务。状态为 `失败`，因为可用性或任务完成维度不满足，不能把拒答写成安全阻断。

### 示例 D：没有测试授权

某用例需要连接真实外部服务，而当前计划仅允许本地模拟器。状态为 `未授权/不执行`，不发送请求，也不计入通过率。

### 示例 E：只有设计没有执行

已经写好训练成员推理用例，但缺少已知成员/非成员集合、模型版本和统计基线。状态为 `待实测`，不能填写虚构结果。

## 10. 创建与复核检查清单

### 设计检查

- [ ] ID 全局唯一，域和学习单元编号正确；
- [ ] 标题不预写结论；
- [ ] 范围、授权、模拟角色、允许和禁止动作完整；
- [ ] 模型、Prompt、规则、索引和工具版本按适用范围记录；
- [ ] 完整无害输入、步骤、控制变量和重复规则明确；
- [ ] 期望行为可观察，判定规则在执行前确定；
- [ ] 停止、清理、回滚和证据路径已经设计。

### 执行检查

- [ ] 当前授权仍有效，环境与前置条件一致；
- [ ] 使用独立 `run_id`，原始结果未被覆盖；
- [ ] 模型、应用和工具行为分层记录；
- [ ] 工具错误、环境错误和模型行为没有混淆；
- [ ] 副作用和停止条件受到监控；
- [ ] 完整证据进入正确存储范围。

### 判定与复测检查

- [ ] 状态只使用五种正式值之一；
- [ ] `阻断` 有实际控制决定与副作用证据；
- [ ] `未授权/不执行` 未计入通过率；
- [ ] 自动与人工判定差异得到保存；
- [ ] 修复前证据未被覆盖，复测使用新 `run_id`；
- [ ] 结论包含限制，没有从单一样本外推整体安全。
