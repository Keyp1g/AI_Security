# 学习单元 13 复盘与学习单元 14 验收准备

> 复盘范围：学习单元 13“AI 安全测试方法论”的流程、统一用例、迁移审计、风险评分、批量评分和作品 5 报告模板。
> 证据边界：结论只覆盖已有本地虚构数据、模拟工具和合成敏感字段；没有新增真实模型、真实平台、网站或外部工具测试。
> 状态口径：`失败`、`待实测`、`阻断`、`通过`、`未授权/不执行`必须分开解释，数量和分数只用于资产管理与排序。

## 1. 本单元形成的统一方法

### 1.1 从测试动作转为可复核流程

本单元把 AI 红队测试整理为 11 个阶段：项目方案、授权与范围、团队与职责、威胁建模、测试设计、受控执行、证据保存、风险评分、修复建议、复测和结构化报告。每个阶段都有输入、产出、责任人、质量门槛和失败时动作，因此测试不再等同于大量尝试攻击 Prompt。

流程中特别区分两种控制：质量门槛用于决定阶段能否交接，缺项时返工或阻断交接；停止条件用于处理中途出现的授权撤销、真实秘密、意外外部连接或不可控副作用，一旦触发就停止执行、保留现场并升级处理。

证据：`notes/unit-13-ai-security-testing.md`。

### 1.2 统一用例字段、命名与状态

统一 schema 把一条用例定义为另一位测试者可以复现和复核的最小单元，主要字段包括：ID、标题与风险类别、范围与授权、前置条件、输入与步骤、期望行为、实际行为、正式判定、影响与评分、证据与复测。

统一 ID 使用“域-学习单元-序号”，例如 `LLM-013-01`、`AGENT-010-03`；历史 ID 不覆盖，必要时通过 `legacy_id` 建立兼容关系。正式状态固定为五种：

| 状态 | 本单元统一含义 | 统计边界 |
|---|---|---|
| `待实测` | 有设计，但没有决定性执行证据 | 不计入通过率，不能写成发现已确认 |
| `通过` | 允许任务完成且所有预注册安全维度满足 | 只证明本次环境和样本 |
| `失败` | 实际行为偏离预注册期望 | 应进入修复与复测 |
| `阻断` | 候选动作真实出现，确定性控制按预期拒绝 | 保留阻断点和副作用证据，不冒充失败或整体通过 |
| `未授权/不执行` | 授权、环境或数据前置不满足 | 不执行，也不计入通过率 |

证据：`cases/llm-security/case-schema.md`。

### 1.3 统一历史资产迁移口径

迁移审计覆盖 Prompt Injection、RAG、Agent 和隐私四类资产，共盘点 64 条历史用例；按新 schema 的严格口径，当前完整用例为 0/64，说明“已经有用例”不等于“已经完成结构化迁移”。本单元只完成 12 条代表性映射，每类 3 条，并把缺口分为：

- 缺少设计：范围、正式五态、主判定层、评分与复测字段不统一；
- 缺少执行：训练隐私、日志平台、真实 IAM、动态 ACL、并发和事务等尚未实测；
- 缺少证据：最终 UI 决定、统一 run ID、持续时间、主体/权限范围、证据哈希和独立复核仍有缺项。

证据：`cases/llm-security/unit-13-case-normalization.md`。

### 1.4 统一风险排序而不制造安全结论

风险评分采用严重性 S、可复现性 R、影响范围 I、利用复杂度得分 C 四个 1–5 分维度，总分范围 4–20。C 分越高表示触发门槛越低。总分只在相同状态组和相近证据成熟度内辅助排序，不能替代人工判断，也不能表示发生概率。

批量评分选择四类资产各 5 条，共 20 条：失败 11 条、待实测 2 条、阻断 7 条。行动队列先按“已确认失败、待验证风险、已阻断场景”分组，再在组内参考分数。12 分以上项目都有证据引用和人工复核标记；其中 `LLM-012-11` 只有设计证据，继续保持“待验证风险”。

证据：`labs/unit-13-risk-scoring.md`、`labs/unit-13-batch-scoring.md`。

### 1.5 统一报告的结论纪律

作品 5 模板固定了文档控制、摘要、授权与范围、架构与信任边界、方法与评分、发现清单、单项发现、未验证项和附录九类主体章节。每项发现必须分别填写“观察事实”“风险推断”“限制”，并关联用例、run/证据、评分、根因、修复和复测。

模板已登记 5 条本地候选发现；`LLM-012-11`、`LLM-012-01` 单列为待验证风险，`AGENT-010-14`、`AGENT-010-11` 单列为已阻断控制。这个分组避免把高潜在影响的阻断项或设计项写成已确认漏洞。

证据：`reports/agent-security-assessment/assessment-template.md`。

## 2. 评分中最大的主观性来源

| 主观性来源 | 容易出现的偏差 | 本单元约束 | 仍需谁参与 |
|---|---|---|---|
| 严重性的业务含义 | 把合成数据等同真实数据，或只看技术现象忽略资产价值 | 4–5 分必须区分已观察影响和潜在影响 | 产品负责人、数据负责人 |
| 可复现性的证据成熟度 | 单次结果因“看起来明显”被打成稳定复现 | 单次观察通常为 2 分；待实测通常为 1 分 | 测试人员、技术复核人 |
| 确定性模拟器的外推 | 把固定代码分支稳定误写成真实集成稳定 | 高复现分只描述该固定实现，不覆盖生产集成 | 应用/平台负责人 |
| 影响范围 | 因用例数量多而夸大范围，或把共同根因重复计算 | 范围必须由角色、组件、共享根因证据支持 | 技术复核人、产品负责人 |
| 利用复杂度得分 | 把“技术复杂”误解为高分 | C 越高表示门槛越低，与严重性独立 | 评分人、复核人 |
| 状态归一化 | 把旧 `PASS`、`needs_review` 或后置缓解直接写成通过 | 依据候选动作、控制决定和主判定层归一为五态 | 独立复核人 |
| 根因归并 | 将同一 RAG 或隐私根因拆成多个系统漏洞 | 关联根因族，保留样本但不重复放大影响 | 技术复核人 |

因此，风险评分最适合回答“在当前证据下先处理什么”，不适合单独回答“系统是否安全”或“风险发生概率是多少”。

## 3. 当前缺失或不充分的证据

### 3.1 隐私

- `LLM-012-01` 至 `LLM-012-04` 缺成员/非成员真值、统计基线、模型版本和实际查询结果；继续保持待实测。
- `LLM-012-09` 至 `LLM-012-12` 缺模拟日志平台上的 IAM 决定、字段级读取、批量导出、审计、保留和删除传播证据。
- 上下文泄露样本已证明合成值进入部分原始响应，但不证明训练数据泄露，也不外推到其他模型或真实敏感数据。

### 3.2 RAG

- `needs_review_untrusted_context` 之后的最终 UI 是否停止展示，仍缺独立展示证据。
- 污染对照的旧记录缺主体、`allowed_scopes` 和完整授权决定；原 JSONL 保持不变，后续新 run 补齐。
- 尚未覆盖真实向量库、动态 ACL、缓存、索引回滚和删除传播。

### 3.3 Agent

- 本地模拟器证明确定性 allowlist、Schema、对象/参数/工具授权、确认和幂等分支的行为，但不证明真实 Agent、IAM 或外部工具集成。
- 历史 JSONL 缺统一独立 run ID、持续时间和部分完整参数；新执行应按统一 schema 保存。
- 并发幂等、事务、TOCTOU 和真实回滚仍未验证。

### 3.4 Prompt Injection 与处置闭环

- 部分失败已有应用层阻断，但模型层失败没有因此消失；修复后仍需建立新 run ID 复测，不能覆盖旧记录。
- 当前批量评分是 20 条代表性样本，不是全部 64 条资产的评分或完整迁移。
- 评分表中的“人工复核标记”表示必须复核，不表示真实产品风险委员会已经批准。

## 4. 报告模板如何防止过度结论

1. 文档控制区要求版本、授权引用、证据批次和多类审阅人，避免无来源结论进入正式报告。
2. 总体结论和单项发现都强制拆分观察事实、风险推断和限制，避免把条件性推断写成已观察事实。
3. 正式状态、证据成熟度和行动队列分开，待实测、阻断和未授权不会被并入“通过”或“已确认漏洞”。
4. 每条发现必须回到用例 ID、证据路径、环境版本、评分理由、修复责任人和新复测记录。
5. 共享根因必须关联，不能凭样例数量重复放大系统级风险。
6. 模板显式禁止用用例数量、平均分、最高分或模板完整度证明系统安全。
7. 未验证项、残余风险和后续计划是必填章节，使报告保留真实平台、集成和复测限制。

## 8. 单元结论与下一入口

学习单元 13 已把分散的测试活动组织为“授权与范围—用例—执行—证据—评分—修复—复测—报告”的可追踪链。当前可以确认的是：统一方法和模板已经形成，12 条代表性用例完成映射，20 条样例完成状态感知评分，5 条候选发现已经关联本地证据。当前不应声称的是：64 条历史用例已经全部迁移、真实系统已经通过评估、待实测风险已经发生、阻断项就是漏洞，或修复已经完成复测。

进入学习单元 14 后，首先从 `notes/stage-02-application-security-glossary.md` 建立术语与薄弱项基线，再由学习者独立完成 30 道自测；随后才能用自测错因、完整性审计和 readiness 文档完成阶段 2 验收。
