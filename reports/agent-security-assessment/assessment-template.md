## 2. 摘要与总体风险结论

### 2.1 评估目标

用 2–4 句说明本次评估要验证的系统能力、角色、关键资产和安全问题。不得只写“测试系统是否安全”。

### 2.2 结果摘要

| 状态 | 数量 | 统计口径 |
|---|---:|---|
| 已确认失败 | `[N]` | 有实际执行证据且偏离预注册期望 |
| 已阻断 | `[N]` | 确定性控制实际阻断，保留候选请求和副作用证据 |
| 待实测 | `[N]` | 只有设计或缺少决定性证据，不计入通过率 |
| 通过 | `[N]` | 允许任务完成且必需安全维度满足 |
| 未授权/不执行 | `[N]` | 不计入通过率 |

### 2.3 总体结论

必须分别写：

- **已观察事实**：本次在哪个环境、版本和用例中实际观察到什么；
- **风险推断**：这些事实对虚构系统可能意味着什么；
- **限制**：哪些模型、真实平台、组件、角色和集成没有验证。

禁止使用“系统安全”“风险已消除”等无范围结论。用例数量、平均分、最高分和模板完整度均不能作为总体安全结论。

### 5.2 用例状态

| 总分与等级 | `[N]/20`、`[LEVEL]` |
| 人工复核 | `[REVIEWER_AND_RESULT]` |

#### 观察事实

只写实际证据直接支持的内容：输入、原始输出、应用/工具决定、阻断阶段、原因码和副作用。不得在本节写假设影响。

#### 风险推断

说明若同一根因存在于目标架构中可能产生的影响，并明确推断所依赖的条件。不得把模拟值描述成真实数据泄露。

#### 限制

记录模型、样本、重复次数、模拟器、缺少的集成和不能外推的范围。

#### 根因

区分模型行为、应用编排、授权、数据治理、工具契约、输出处理和日志控制。若只有症状证据，写“根因待确认”。

#### 修复建议

| 责任组件 | 修复动作 | 所有者 | 验收条件 | 临时缓解/回滚 |
|---|---|---|---|---|
| `[COMPONENT]` | `[ACTION]` | `[OWNER]` | `[TESTABLE_CRITERIA]` | `[CONTAINMENT]` |

#### 复测

| 原 run ID | 修复版本 | 新 run ID | 复测状态 | 证据 | 残余风险 |

| `[OLD-RUN]` | `[FIX_VERSION]` | `[NEW-RUN]` | 待复测/通过/失败/阻断 | `[REF]` | `[RESIDUAL]` |

## 11. 模板验收
