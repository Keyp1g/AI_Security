## 1. 三层模型

三层模型是分析视角，不是固定的物理部署结构。同一个组件可能在不同系统中被合并或拆分，因此按职责、数据流和信任边界分析，比按主机或进程划分更稳定。

| 层 | 职责 | 典型对象 | 主要问题 |
|---|---|---|---|
| 使用层 | 用户/业务侧交互、输入输出和人工流程 | 用户、角色、聊天界面、API 客户端、管理员操作 | 谁能输入什么、看到什么、触发什么？ |
| 应用层 | AI 应用编排、Prompt、RAG、Agent 和业务规则 | 编排服务、检索、工具路由、输出渲染、策略判断 | 不可信输入是否改变流程或越过业务规则？ |
| 平台层 | 提供模型、数据、身份、网关、运行时和审计底座 | 模型服务、向量库、IAM、密钥、队列、日志 | 平台如何隔离主体和租户、保护数据并强制执行控制？ |

应用层负责决定业务流程和安全策略，平台层提供受控执行能力，使用层决定主体、入口和结果如何被人使用。三层之间通过身份、权限、数据来源、输出审查和审计证据连接。

## 2. 教材内容与本日分析框架

教材对应章节将 LLM 应用描述为由编排组件连接用户、检索信息和模型生成响应的系统。教材明确强调的应用视角是：用户请求进入应用，应用引导请求至正确组件并取得附加信息，再由 LLM 生成响应；应用还要处理错误、记录信息和跟踪对话上下文。

本日的“使用层、应用层、平台层”是学习计划提供的分析框架。它是根据组件职责和信任边界进行的合理组织，不应被写成教材原文或所有产品都采用的实际拓扑。

## 3. 模拟 AI 客服的最小组件

| 组件 | 主要资产 | 入口 | 信任假设 | 控制者 |
|---|---|---|---|---|
| 用户渠道 | 会话与凭证 | 聊天接口 | 用户输入不可信且仅代表当前主体 | 产品/安全团队 |
| API 网关 | 请求、限额和路由状态 | HTTP/API 请求 | 请求必须先通过身份和速率控制 | 平台团队 |
| 身份与会话管理 | 主体、角色、租户和会话 | 登录、令牌和会话续期 | 客户端不能自行声明角色 | IAM 团队 |
| 对话编排 | 请求状态、Prompt 上下文和流程 | 用户消息、检索结果、工具结果 | 外部内容默认是数据，不是指令 | 应用团队 |
| Prompt 模板 | 系统规则、任务范围和输出契约 | 模板配置与变量填充 | 模板版本受控且变量边界明确 | 应用/安全团队 |
| RAG 知识库 | 知识文档、客户数据和索引 | 查询、文档接入和索引更新 | 内容必须经过来源、版本、权限和信任验证 | 数据所有者/知识运营 |
| 模型服务 | 模型请求、响应和调用配额 | 编排层模型调用 | 模型输出是不可信候选结果 | 平台团队 |
| 工具/业务 API | 订单、退款和 PII | Agent 工具调用 | 模型意图必须经服务端授权才能执行 | 业务系统/IAM/风控 |
| CRM/订单库 | 客户和订单状态 | 业务 API 查询或更新 | 对象级权限由权威业务系统判断 | 业务系统所有者 |
| 日志审计 | 决策元数据和证据引用 | 各组件事件 | 日志最小化、防篡改、可关联 | 平台/安全团队 |
| 输出渲染器 | 面向用户的文本或结构化结果 | 模型响应和审查结果 | 输出必须经过解析、编码和敏感信息检查 | 应用团队 |

## 4. 跨层数据流与授权边界

典型流程如下：

```text
用户输入
  -> 渠道与会话
  -> 应用编排和 Prompt 组装
  -> RAG 检索或 Agent 规划
  -> 模型服务
  -> 工具候选调用
  -> 应用策略判断
  -> 平台网关/IAM/业务 API 再授权
  -> 执行或拒绝
  -> 输出审查与展示
  -> 审计记录
```

用户输入和输出展示主要属于使用层，但会分别由应用层接收和生成；Prompt 组装属于应用层；RAG、模型和工具调用通常由应用层编排、由平台层提供或执行能力，因此跨越应用层与平台层。

### 场景：visitor 查询他人订单

用户是 `visitor`，通过聊天输入要求 Agent 查询另一客户的订单。模型生成合法 JSON，工具参数也符合 Schema。

1. 应用层的 Agent 编排或策略引擎应在工具执行前依据服务端会话、角色、租户、对象归属和业务策略拒绝请求。
2. 平台层的工具网关、IAM 和业务订单 API 必须再次强制执行授权，不能把应用层的判断当作唯一边界。
3. 使用层可以隐藏按钮或展示拒绝提示，但不能承担安全授权职责。
4. 必须验证主体身份与会话有效性、角色和数据范围、工具权限、目标订单归属、允许字段、参数组合及必要的同意或代理依据。
5. 日志至少应关联请求 ID、时间、主体/会话引用、策略版本、工具和参数摘要、授权决定、拒绝阶段、原因码、结果和告警状态。完整 Prompt、模型响应或敏感原文进入访问受控的证据区，普通日志保存哈希、摘要或证据 ID，避免不必要的 PII。

合法 JSON 只证明字段、类型和格式符合工具契约，不证明身份有效、对象属于当前主体、角色有权访问或业务规则允许该操作。模型可能被不可信输入诱导生成形式正确的调用，因此结构校验不能替代模型外授权。

### 数据流、信任级别与证据

信任级别说明内容能否作为权限或控制流依据：`不可信数据` 只能作为待处理内容；`已验证身份/元数据` 可用于策略输入，但仍需检查范围和时效；`候选动作` 尚未授权；`已授权请求` 仅在执行前的确定性检查通过后成立。

| 流 | 方向与数据 | 信任级别 | 主要越权/失效点 | 可记录证据 |
|---|---|---|---|---|
| F1 | 使用层用户 -> 客户端：消息、附件 | 不可信数据 | 伪造身份声明、恶意/超长输入、敏感数据误提交 | request ID、渠道、输入大小、附件 ID/哈希；原文仅按需进入受控证据区 |
| F2 | 客户端 -> 网关：请求、Cookie/Token | 未验证凭证 | 会话混淆、过期或重放凭证、缺少限额 | 请求 ID、认证结果码、会话引用、限流决定；不记录令牌原文 |
| F3 | 身份服务 -> 编排器：主体、角色、租户、范围 | 经服务端验证的身份声明 | 错误主体绑定、陈旧角色、跨租户范围扩大 | actor/session 引用、角色/租户、身份源、策略版本、时间戳 |
| F4 | 编排器 -> Prompt/Agent：用户任务、历史和上下文 | 混合信任；外部内容仍不可信 | 来源标签丢失、跨会话记忆混入、指令与数据混淆 | 输入来源 ID、上下文成员 ID、模板版本、内容哈希 |
| F5 | 应用 -> 模型网关：Prompt、检索上下文、参数 | 含不可信数据的模型请求 | 敏感上下文过量、租户隔离错误、模板版本漂移 | model/deployment ID、参数、模板版本、请求哈希、上下文来源 ID |
| F6 | 模型服务 -> Agent：文本或结构化候选输出 | 不可信模型输出 | 幻觉、注入影响、伪造权限字段、无效结构 | 原始响应的受控证据引用、响应哈希、解析/校验结果 |
| F7 | 检索服务 -> 文档库/索引：查询与授权范围 | 查询不可信；范围来自服务端 | 先检索后鉴权、客户端伪造范围、跨租户召回 | 主体范围、索引版本、过滤条件、候选 ID 与分数 |
| F7b | 索引 -> 上下文组装：候选片段与元数据 | 内容不可信；元数据须验证 | 污染片段进入上下文、版本/权限元数据丢失 | document/chunk ID、来源、版本、trust level、最终上下文 ID |
| F8 | Agent -> 工具路由：工具名和参数 | 候选动作，未授权 | 模型选择越权工具、参数扩大对象/字段范围 | tool name、参数键、参数摘要/哈希、模型响应关联 ID |
| F9 | 工具路由 -> 授权层：通过 Schema 的候选请求 | 结构有效但仍未授权 | 将 Schema 通过误当成业务许可 | Schema 版本、校验结果、拒绝阶段和原因码 |
| F10 | 应用 -> 工具网关：工具调用 | 待授权请求 | 缺少主体绑定、二次检查或副作用确认 | actor/session 引用、tool、object ref、参数摘要、request ID |
| F11 | 网关/IAM -> 业务 API：已授权请求 | 仅对本次主体、对象、动作和参数范围有效 | TOCTOU、对象归属错误、重放、幂等缺失 | policy version、allow/deny、object scope、确认引用、幂等键摘要 |
| F12 | 业务 API -> Agent：工具结果 | 不可信工具数据 | 返回内容携带控制样式文本、敏感字段过量 | 工具结果 ID、Schema 结果、字段白名单、结果哈希 |
| F13 | 输出审查 -> 使用层：最终响应 | 经应用审查的展示内容，不是权限证明 | XSS/渲染问题、敏感信息泄露、错误引用 | 输出决定、编码/Schema 检查、脱敏规则版本、响应 ID |
| F14 | 各组件 -> 日志：事件和审计元数据 | 受控审计数据 | 日志注入、敏感原文过度留存、关联字段缺失 | request ID、时间、actor 引用、决定、阶段、策略版本、证据引用 |
| F15 | 管理员 -> 管理控制面：配置、策略、索引变更 | 高权限管理输入 | 管理面身份失陷、未审批变更、审计缺口 | 操作者、变更前后版本/哈希、审批引用、时间和回滚 ID |

普通日志应优先保存关联 ID、决定元数据、参数键/哈希和证据引用；完整 Prompt、响应、文档正文或工具返回原文只在确有需要时进入访问受控、设有保留期限的证据区。

### 计划要求的三个问题

1. **哪些风险只在模型输出层可见，哪些必须由应用或平台控制？**
   输出层可观察到格式破坏、危险内容、引用缺失、敏感字段暴露或渲染风险；但身份伪造、对象级越权、租户隔离、工具副作用和资源耗尽必须由应用/平台的确定性控制阻止或限制。输出审查可以检测并阻断部分结果，不能证明上游没有越权读取，也不能撤销已发生的副作用。

2. **Prompt Injection、RAG、Agent、输出安全分别落在哪些层，为什么会跨层？**
   Prompt Injection 常从使用层输入或外部文档进入，在应用层影响上下文和流程，并可能借平台工具能力产生影响；RAG 由应用层编排检索，依赖平台索引/存储与身份范围，且检索内容会进入模型上下文；Agent 规划和路由属于应用层，模型与工具运行能力属于平台层，授权和执行出口横跨两层；输出安全从应用层解析/审查延伸到使用层展示，并依赖平台日志和数据保护。

3. **模型输出正常但服务端鉴权缺失，系统是否仍然安全？**
   否。服务端鉴权缺失时，格式正常或内容无害的输出仍可能基于越权读取的数据生成，也可能由后续组件执行越权动作。模型文本不能替代身份、对象权限和业务规则检查。

### 为什么不能由单层控制独立解决

以 Prompt Injection 导致 Agent 工具滥用为例：使用层可以限制输入和提示用户，但不能识别所有表达；应用层可以标记来源、隔离上下文、约束模型输出并校验工具 Schema，但模型仍可能产生形式正确的越权候选动作；平台层和业务 API 能强制执行身份、对象和参数授权，却无法单独判断某段外部文档是否应参与当前任务。完整控制链需要三层协作：

```text
使用层：明确主体、入口和风险提示
  -> 应用层：来源标记、上下文隔离、候选动作校验
  -> 平台层：身份/对象授权、最小权限、受控执行与审计
  -> 应用/使用层：输出审查、展示和人工复核
```

任何单层失效都可能留下缺口：只过滤输入不能阻止间接注入，只约束 Prompt 不能提供强制授权，只在平台做权限检查也不能保证回答的事实性、引用正确性或安全展示。
