## 3. 核心概念摘录

以下解释采用“自己的话 + 安全联系”的形式。`[待查]` 表示第一天只完成术语盘点。

| 主题 | 用自己的话解释 | 与 AI 安全的关系 |
|---|---|---|
| 传统网络安全 | 保护系统、接口、设备和数据的保密性、完整性、可用性，防止未授权访问、篡改和中断。 | AI 应用仍依赖 Web、API、操作系统和数据库，因此仍需防范注入、越权、SSRF、文件上传和数据泄露。 |
| AI 安全 | 保护 AI 系统的训练数据、模型、推理过程、应用组件、输出和使用方式。 | 风险除了传统漏洞，还包括数据投毒、模型逃逸、成员推断、隐私泄露、偏见和不安全生成。 |
| 攻击面 | 攻击者可能影响系统或获取权限的入口和资产集合。 | AI 应用的攻击面横跨用户输入、上下文、知识库、模型、API、插件/工具、日志和输出。 |
| 数据隐私 | 对个人数据、敏感业务数据及其流转、存储和使用进行保护。 | 训练集、会话记录、上传文件、RAG 文档和模型输出都可能泄露敏感信息。 |
| 可解释性 | 能说明模型为何产生某个预测或回答，以及依据了哪些输入。 | 黑箱决策会增加错误排查、风险复核和责任追踪的难度，不能只凭模型结果做高风险决策。 |
| LLM（大语言模型） | 在大量文本上训练、通过语言 token 预测和生成文本的模型。 | 需要关注提示注入、越狱、幻觉、训练数据泄露、上下文泄露和输出被下游执行。 |
| Transformer | 以注意力机制为核心、适合并行处理序列的神经网络架构，是现代 LLM 的重要基础。 | 注意力会把用户输入、系统指令和外部文档放入同一上下文，边界混淆时可能导致指令覆盖或数据泄露。 |
| RAG（检索增强生成） | 先从外部知识库检索相关内容，再把检索结果交给模型生成回答。 | 需要防范恶意文档/提示注入、越权检索、跨租户数据混淆、检索污染和引用伪造。 |
| Prompt | 给模型的任务、约束、上下文和输出要求。 | Prompt 不是可靠的权限边界；不能只靠一句系统提示保护高权限工具或敏感数据。 |
| NLP（自然语言处理） | 让计算机处理、理解和生成自然语言的一组方法。 | 自然语言既是数据也是控制信号，攻击者可以通过改写、编码、多轮对话影响模型行为。 |
| Embedding（嵌入） | 将文本或其他对象映射为可比较的数值向量。 | 向量库中的权限、租户隔离、删除同步和检索范围必须受控，否则可能造成越权检索。 |
| 幻觉 | 模型生成听起来合理但与事实、上下文或证据不一致的内容。 | 可能导致错误安全建议、错误代码或错误业务决策；需要引用、校验和人工复核。 |
| 偏见 | 模型因训练数据或目标设计而对群体、观点或情境产生系统性不公平倾向。 | 影响公平性、合规性和决策可靠性，需要数据检查、评测和申诉机制。 |
| Jailbreak（越狱） | 通过特殊提示或对话策略诱导模型绕过既定安全限制。 | 说明模型拒答不是完整安全控制，必须叠加输入检测、输出检查、权限控制和审计。 |

## 4. AI 安全与传统 Web 安全

### 联系

AI 应用通常仍由网页、API、身份认证、数据库、文件系统和云基础设施组成，因此传统的保密性、完整性、可用性，以及认证、授权、输入校验、日志审计等控制仍然适用。传统漏洞还可能被模型的自动化能力放大，例如模型被诱导调用存在 SSRF 的工具。

### 区别

| 维度 | 传统 Web 安全 | AI/AI 应用安全 |
|---|---|---|
| 执行逻辑 | 主要由相对确定的程序逻辑控制 | 自然语言输入、模型推理和生成输出带来非确定性 |
| 攻击面 | 网络边界、服务、接口、操作系统和数据库 | 在上述基础上增加训练数据、模型、上下文、向量库和工具调用 |
| 输入性质 | 参数通常有明确类型和协议边界 | 用户输入、外部文档和检索结果可能同时成为数据与指令 |
| 主要风险 | 注入、越权、认证缺陷、SSRF、RCE、数据泄露 | 提示注入、越狱、幻觉、数据投毒、隐私泄露、模型窃取和不安全输出 |
| 防护重点 | 代码修复、边界校验、权限和隔离 | 在传统控制上增加上下文隔离、最小权限、工具审批、输出验证和持续评测 |

### 当前结论

AI 应用安全不是简单地给 Web 安全加一个输入过滤器。它是 Web/AppSec、模型安全、数据安全和权限治理的交叉问题。模型可以被视为“不完全可信、但可能拥有行动能力的代理”，因此不能让模型本身充当最终权限判断者。

## 5. AI 应用的攻击面草图

```text
用户/外部内容
      |
      v
输入与会话层 ----> Prompt/上下文拼接 ----> 模型推理层
      |                       |                  |
      |                       v                  v
身份认证/授权             RAG/向量库          输出处理
      |                       |                  |
      +-------------> 工具/API/数据库 <---------+
                              |
                         日志、审计、监控
```

需要重点追踪的数据流：

1. 用户输入是否与系统指令、外部文档发生了不可信的混合。
2. 检索结果是否经过租户、用户和文档级权限检查。
3. 模型是否可以直接决定调用邮件、文件、数据库、网络或代码执行工具。
4. 输出是否会被 HTML、Markdown、Shell、SQL、浏览器或下游业务自动解释。
5. 每次输入、检索、工具调用和输出是否留下可复核的审计证据。

一个典型风险链条是：

```text
恶意文档注入指令
  -> 文档进入检索结果
  -> 模型把内容误当成高优先级指令
  -> 调用权限过大的工具
  -> 读取内部数据
  -> 通过 Web/API/输出渠道泄露
```

### 复盘问题

1. 为什么第一天先做索引和基线，而不是直接研究越狱？  
   因为没有资料入口、术语地图和能力基线，后续容易无边界阅读，也无法判断“看过”与“会做”的差别。先建立证据链，才能按优先级补基础并验证进步。

2. 模型、应用、数据、工具和输出是什么关系？  
   模型负责推理和生成，应用负责编排请求与流程，数据提供上下文，工具把模型能力连接到外部系统，输出可能被用户或下游程序继续执行。它们通过数据流和权限串联，因此任一层的注入、越权或泄露都可能扩散到其他层。

- 可以做：同一问题多次输出对比，记录温度、上下文和指令清晰度的影响。
