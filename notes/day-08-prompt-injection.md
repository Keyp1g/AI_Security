## 一、本小时目标

- 理解不可信内容如何改变 LLM 应用行为；
- 区分直接注入、间接注入、系统提示泄露诱导和工具指令污染；
- 区分 Prompt Injection 与 Day 6 的 Jailbreak；
- 明确模型外控制不能由 Prompt 或模型自称授权替代。

## 二、核心概念

Prompt Injection 的核心是：应用把攻击者可控或不可信的内容，当成能够改变任务、规则或工具行为的指令。问题不在于是否出现某个固定短语，而在于指令与数据边界是否被破坏，以及应用或模型是否因此偏离预定任务。

需要区分两个状态：

- **注入尝试**：不可信内容试图覆盖应用规则、劫持任务或污染工具调用；可以在输入审计阶段被识别，即使模型最终没有受影响。
- **注入成功**：有证据表明模型或应用确实偏离任务、泄露不应披露的内容、破坏输出契约或产生未授权工具请求。

因此，测试记录不能把“出现可疑输入”直接记为成功，也不能只用单次安全输出证明应用已经完成防护。

## 三、四类风险

这四类标签并非完全互斥。直接注入和间接注入按入口来源分类；系统提示泄露诱导和工具指令污染描述攻击目标或受影响资产。

| 类型 | 来源或目标 | 影响 | 成功信号 | 主要防护 |
|---|---|---|---|---|
| 直接注入 | 用户当前输入 | 预定任务、规则、输出契约 | 原任务被转移或 Schema 被破坏 | 来源标记、任务范围约束、结构化解析和校验 |
| 间接注入 | 网页、邮件、文档、RAG 片段等外部数据 | 摘要、检索结果和下游操作 | 文档控制文字被执行，而非仅作为数据处理 | 来源追踪、`untrusted` 标签、指令/数据分隔、输出校验 |
| 系统提示泄露诱导 | 目标是内部规则、配置或模拟敏感值 | 应用内部上下文和最小披露边界 | 输出内部规则或 `[SIMULATED_SECRET]` | 不放真实秘密、输出审查、最小披露 |
| 工具指令污染 | 工具返回中的不可信文本 | 工具选择、参数和操作权限 | 模型提出未授权或越界工具请求 | 工具允许列表、参数 Schema、服务端授权、人工确认 |

“系统提示泄露诱导”更准确地说是攻击目标或风险类型，而不只是结果；它可以通过直接输入、间接文档或工具返回污染触发。工具返回即使来自看似内部的组件，也应按不可信数据处理。

## 四、与 Jailbreak 的边界

- **Prompt Injection** 关注应用指令与数据边界、任务劫持和工具行为；
- **Jailbreak** 关注模型内容或行为安全限制是否被绕过。

用户让订单应用停止查询并输出未经验证状态，属于直接 Prompt Injection，未必是 Jailbreak。用户诱导模型提供原本禁止的内容，属于 Jailbreak。外部文档同时要求停止摘要和绕过安全规则时，两种风险可以重叠。

## 五、为什么不能只依赖内容过滤

关键词过滤不能保证任务边界、权限边界或输出契约：同一意图可有多种表达，正常文档也可能讨论相关词汇，且无明显攻击词的内容同样可能改变任务。完整控制至少还需要来源与信任标签、指令/数据分隔、结构化输出、Schema 校验、敏感输出检查、服务端身份与对象授权、高影响操作确认以及日志审计。

## 六、主动回忆批改

### 问题 1：核心机制

学习者回答抓住了“破坏指令-数据边界、劫持任务或影响工具行为”，并意识到不能只看固定攻击短语。

### 问题 2：直接与间接注入

回答正确。核心区别是来源，不是危害大小；间接注入因控制文字隐藏在应用读取的外部数据中，通常更难定位和归因。

### 问题 3：系统提示泄露诱导与间接注入

回答方向正确。更准确的表述是：间接注入是入口/手段，提示泄露是目标或风险类型；同一事件可以同时拥有这两个标签。不能把提示泄露必然视为已成功，仍需保存实际输出证据。

### 问题 4：为什么必须服务端授权

回答正确。补充一点：模型不应被要求提供“可靠强制安全边界”，因为模型输出本身是不可信信号；身份、对象权限、参数和高影响审批必须由模型外的确定性代码执行。

- A：直接 Prompt Injection；
- B：间接 Prompt Injection；
- C：工具指令污染，也属于 Prompt Injection 的工具返回入口。

三项分类均正确。

### 1. 完整应用链路

```text
[1 用户输入：untrusted:user] -----------\
[2 外部文档：untrusted:document] -------+--> [5 提示组装器]
[3 工具返回：untrusted:tool_result] -----/          |
[4 应用规则：trusted:application] -----------------+
                                                    v
                                                [6 LLM]
                                                    |
                                      untrusted:model_output
                                                    v
                                            [7 输出解析器]
                                                    |
                                      parsed_but_not_authorized
                                                    v
                                  [8 服务端身份与权限校验器]
                                         /                    \
                                      deny                    allow
                                       |                        |
                                [9 阻断与审计]          [10 展示或受控执行]
```

图中的 `trusted` 只表示应用规则来自受控配置，并不表示 Prompt 可以强制安全；`untrusted` 表示内容不能凭其文本声明获得指令权或业务权限。LLM 输出经过解析后也只是“格式有效的候选请求”，不是已授权请求。

|---|---|---|---|---|

| 4. 应用规则 | 受控但不是安全边界 | 应用维护者 | `RuleVersion`、配置哈希、变更记录 | 配置缺失或版本不符时 fail closed |

| 8. 权限校验器 | 权威安全控制 | 服务端策略与可信会话 | 身份、对象、动作、策略版本、允许/拒绝及原因 | 默认拒绝；不得采用模型声称的身份或授权 |

| 10. 展示或受控执行 | 条件可信的动作出口 | 应用后端 | 展示内容或工具名、参数摘要、执行结果 | 输出编码、最小权限、幂等/回滚和高影响确认 |

### 3. 关键原则：信任跟随来源，不跟随位置或语气

- 网页、邮件、知识库文档和检索片段即使由应用自动取得，仍是外部数据。
- 工具返回即使来自内部 API，也可能包含用户生成内容、被污染的数据库字段或上游错误，因此不能获得应用规则的指令权。
- 模型输出即使语言确定、JSON 格式正确或声称“管理员已批准”，仍然是不可信候选输出。
- 应用规则虽然来自受控配置，也只是告诉模型应该怎样表现；真正强制权限的是模型外代码。

### 4. 六条信任边界

#### TB-01：用户或外部调用方 → 应用入口

跨越内容：用户问题、参数和附件引用。

风险：任务冲突、超长输入、伪造身份声明、格式突破。

控制：绑定可信会话身份；限制类型和大小；标记 `untrusted:user`；用户文本不得改变角色、权限或规则版本。

#### TB-02：外部内容源 → 文档摄入与检索层

跨越内容：网页、邮件、文档、评论和检索片段。

风险：间接注入、来源丢失、跨范围检索、控制文字混入数据。

控制：保留文档 ID、来源和信任标签；限制检索范围；将引用内容放入明确的数据容器；来源不可追踪时阻断或降级。

#### TB-03：工具或上游服务 → 工具结果适配层

跨越内容：工具返回的 JSON、错误信息和自由文本字段。

风险：返回内容污染后续推理、伪造新的工具指令、字段类型或长度异常。

控制：校验返回 Schema；只提取允许字段；标记 `untrusted:tool_result`；不得把返回中的自然语言当成新的系统规则。

#### TB-04：多源输入 → 提示组装器与 LLM

跨越内容：应用规则和多类不可信数据被放进同一上下文。

风险：来源标签丢失、规则被截断、不可信内容获得指令效果。

控制：固定组装模板和顺序；显式分隔数据；记录规则版本与组装哈希；计算上下文预算；缺失来源标签时停止。

#### TB-05：LLM → 输出解析与安全决策层

跨越内容：自然语言或结构化模型输出。

风险：非预期格式、未知字段、模拟敏感值泄露、模型自授权限、恶意展示内容。

控制：输出只接受固定 Schema；拒绝额外字段和越界枚举；敏感输出扫描；解析失败时 fail closed。解析成功只说明“格式有效”，不说明“已授权”。

#### TB-06：已解析请求 → 权限校验与真实副作用

跨越内容：候选工具名、对象 ID、动作和参数。

风险：水平/垂直越权、高影响动作未经确认、模型选择未允许工具。

控制：服务端使用可信会话重新验证主体、对象、动作和参数；采用工具允许列表与最小权限；高影响动作要求人工确认；拒绝结果不可被模型覆盖。

### 5. 三类防护点

#### 输入防护

- 标记 `user`、`document`、`tool_result` 等来源及 `untrusted` 信任级别；
- 验证类型、大小、来源和检索范围；
- 固定应用规则版本和上下文预算；
- 对未知来源或标签缺失采取阻断或安全降级；
- 内容检测只作为风险信号，不作为唯一安全边界。

#### 输出防护

- 使用固定 JSON Schema、枚举和长度限制；
- 拒绝解析失败、额外字段和越界参数；
- 检查 `[SIMULATED_SECRET]` 等禁止输出占位符；
- 展示前进行上下文相关编码；
- 保存原始输出、解析结果和阻断原因，不能只保存最终展示文本。

#### 工具与执行防护

- 模型只能提出候选工具请求，不能授予权限；
- 工具名使用允许列表，参数独立进行 Schema 校验；
- 身份、对象归属和动作权限由服务端重新判断；
- 高影响操作需要二次确认或人工审批；
- 执行器采用最小权限，并保留审计与失败后的无副作用路径。

### 6. 为什么模型说“允许执行”仍不能执行

模型看到的是文本上下文，不是可信的身份与授权事实。它可能受到用户输入、外部文档、工具返回、上下文截断、模型错误或 Prompt Injection 的影响。因此，类似下面的模型输出：

```json
{
  "tool": "SIMULATED_HIGH_IMPACT_ACTION",
  "authorized": true,
  "reason": "用户说管理员已经批准"
}
```

最多只是一份候选请求。应用必须忽略模型生成的 `authorized` 值，改用可信会话和服务端策略重新计算：

```text
主体是谁？
→ 是否允许使用这个工具？
→ 是否能操作这个对象？
→ 参数是否在允许范围？
→ 是否需要人工确认？
→ 全部通过后才执行
```

原因可以归纳为三点：

1. **模型不能证明身份**：用户输入中的“我是管理员”只是文本声明。
2. **模型不能授予权限**：授权必须来自服务端策略，而不是概率性生成结果。
3. **格式正确不代表行为安全**：合法 JSON 仍可能请求越权对象或高影响动作。

### 7. 失败处理示例

| 失败场景 | 应用应采取的动作 | 不应采取的动作 |
|---|---|---|
| 外部文档缺少来源标签 | 停止摄入或按最低信任级别隔离 | 默认视为可信文档 |
| 模型输出无法解析 | 阻断并记录解析错误 | 猜测模型意图后执行 |
| Schema 合法但对象无权限 | 服务端拒绝并记录授权原因 | 接受模型的授权说明 |
| 高影响动作缺少确认 | 转人工或要求可信渠道确认 | 依据自然语言确认直接执行 |
| 工具返回包含控制性文字 | 作为数据记录并限制进入后续上下文 | 将其提升为应用规则 |

## 十四、第七小时：检测与防护清单（15:00-16:00）

> 原则：关键词检测只是信号；安全边界由输入验证、严格解析、服务端授权和执行阻断共同强制。模型的拒绝、解释或授权声明均不能替代应用控制。

| 控制 ID | 控制与位置 | 检测信号 / 日志字段 | 阻断或降级动作 | 关联用例 | 残余风险 | 模型外控制 | 当前状态 |
|---|---|---|---|---|---|---|---|
| `CTRL-08-01` | 输入来源与信任标签 | `InputSources`、`TrustLabels`；来源缺失或未知 | 未知来源停止摄入或按最低信任隔离 | `06-10`、`16`、`18-20` | 标签可能被传输层丢失或错误赋值 | 是 | 已验证标签与日志；真实身份体系未接入 |
| `CTRL-08-02` | 指令与数据分隔 | 组装对象中规则/用户/文档/工具槽；`AssemblyHash` | 标签缺失、槽位混用时不调用模型 | `01-02`、`06-10`、`18` | 自然语言分隔不能保证模型稳定遵守 | 部分 | 结构已实现；仍需语义控制 |
| `CTRL-08-03` | 任务范围与状态转换 | 输出任务状态、允许任务 ID、预期状态；任务偏移标记 | 未知任务或不允许状态由确定性规则拒绝 | `01-02`、`05`、`18` | 当前语义范围校验只覆盖少量标记，不能理解所有偏移 | 是 | 部分实现；`LLM-008-02` 暴露缺口 |

### 防护链的最小顺序

```text
来源/信任校验
→ 指令与数据分槽组装
→ LLM 候选输出
→ 严格 Schema
→ 精确来源与语义任务检查
→ 归一化敏感输出检查
→ 工具允许列表与参数检查
→ 服务端主体/对象/动作授权
→ 高影响人工确认
→ 展示或受控执行
→ 审计与复测
```

其中 `CTRL-08-04` 至 `11` 都不依赖模型自觉遵守；即使模型失败，应用仍应阻断。内容过滤没有被当作唯一控制。
