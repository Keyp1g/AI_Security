## 1. 三层模型

三层模型是分析视角，不是固定的物理部署结构。同一个组件可能在不同系统中被合并或拆分，因此按职责、数据流和信任边界分析，比按主机或进程划分更稳定。

| 层 | 职责 | 典型对象 | 主要问题 |
|---|---|---|---|
| 使用层 | 用户/业务侧交互、输入输出和人工流程 | 用户、角色、聊天界面、API 客户端、管理员操作 | 谁能输入什么、看到什么、触发什么？ |
| 应用层 | AI 应用编排、Prompt、RAG、Agent 和业务规则 | 编排服务、检索、工具路由、输出渲染、策略判断 | 不可信输入是否改变流程或越过业务规则？ |
| 平台层 | 提供模型、数据、身份、网关、运行时和审计底座 | 模型服务、向量库、IAM、密钥、队列、日志 | 平台如何隔离主体和租户、保护数据并强制执行控制？ |

应用层负责决定业务流程和安全策略，平台层提供受控执行能力，使用层决定主体、入口和结果如何被人使用。三层之间通过身份、权限、数据来源、输出审查和审计证据连接。

## 2. 教材视角与分析框架

教材将 LLM 应用描述为由编排组件连接用户、检索信息和模型生成响应的系统：用户请求进入应用，应用引导请求至正确组件并取得附加信息，再由 LLM 生成响应；应用还要处理错误、记录信息和跟踪对话上下文。

本日的“使用层、应用层、平台层”是学习计划提供的分析框架。它根据组件职责和信任边界组织风险，不应被理解为教材原文或所有产品都采用的实际拓扑。

## 3. 逻辑攻击面图

以下是本地虚构 AI 客服/RAG/Agent 的逻辑模型。`[U]` 表示使用层，`[A]` 表示应用层，`[P]` 表示平台层，`TB` 表示信任边界。

```text
 [U] 客户/支持人员/管理员
       | 消息、附件、会话引用
       v
 [U] Web/移动端/API 客户端
       | HTTPS 请求、Cookie/Token
       v  TB1：外部主体 -> 服务端身份域
 [P] API Gateway + 身份/会话服务
       | 已验证主体、角色、租户、请求 ID
       v
 [A] 对话编排器 -----> [A] 业务策略/授权检查
       |                             |
       v                             v
 [A] Prompt 组装器             [A] Agent 规划器
       |                             | 候选工具名与参数
       +-----------> [P] 模型网关/API [A] 工具路由与 Schema 校验
                         |                     |
                         v                     v
                     [P] 模型服务       TB2：应用 -> 工具执行域
                                               |
          +------------------------------------+----------------+
          | 查询、授权范围                     | 工具请求
          v                                    v
 [P] 文档库/向量索引                  [P] 工具网关/IAM
          | 候选片段、来源/权限元数据          | 授权后的请求
          +-----------> [A] 检索过滤/上下文组装 v
                                         [P] 订单/工单模拟 API
                                               | 结构化结果
                                               v
 [A] 输出解析、引用/敏感信息审查 <--- 工具结果隔离与再规划
       | 经审查的响应
       v
 [U] 客户/支持人员界面

 所有层 -- 最小化事件、决定元数据、证据引用 --> [P] 日志/审计系统
 [P] 管理员 -- 配置/策略/索引变更 --> [A/P] 管理控制面
```

## 4. 跨层数据流与控制责任

| 数据流 | 主要风险 | 首要控制 | 证据 |
|---|---|---|---|
| 用户输入 -> 客户端/应用 | 恶意输入、敏感数据误提交、超长请求 | 输入边界、限额、来源标记 | 请求 ID、渠道、大小、附件 ID/哈希 |
| 客户端 -> 网关/身份服务 | 会话混淆、凭证重放、角色伪造 | 服务端身份验证、会话绑定、限流 | 会话引用、认证结果码、主体引用 |
| 身份服务 -> 编排器 | 陈旧角色、租户范围错误 | 从可信会话取身份，执行时重新授权 | 角色、租户、范围、策略版本 |
| 编排器 -> Prompt/Agent | 指令与数据混淆、来源标签丢失、记忆串户 | 上下文分区、来源标签、模板版本控制 | 模板版本、上下文成员 ID、内容哈希 |
| 应用 -> 模型服务 | 上下文过量、敏感数据泄露、模型输出幻觉 | 最小上下文、结构化输出、输出审查 | 模型/部署 ID、参数、请求哈希、响应引用 |
| 索引 -> 上下文组装 | RAG 污染、越权召回、版本残留 | 来源/版本/权限/信任验证，权限先于生成 | 文档/分片 ID、ACL、trust level、最终上下文 ID |
| Agent -> 工具路由 | 越权工具、参数扩大、模型伪造确认 | allowlist、严格 Schema、身份/对象/参数授权 | 工具名、参数摘要/哈希、拒绝阶段 |
| 工具网关 -> 业务 API | TOCTOU、对象归属错误、重放和重复副作用 | 执行前再授权、确认、幂等、业务系统兜底 | policy version、对象范围、确认引用、幂等键摘要 |
| 工具结果 -> 再规划/输出 | 返回内容污染、敏感字段过量、伪造控制文字 | 结果 Schema、字段白名单、`untrusted_tool_result` 标记 | 结果 ID、字段校验、结果哈希 |
| 输出审查 -> 用户界面 | 敏感信息、错误引用、渲染风险 | 编码、结构校验、脱敏和引用审查 | 输出决定、规则版本、响应 ID、证据引用 |
| 各组件 -> 审计系统 | 日志注入、原文过度留存、缺少关联 ID | 最小化日志、防篡改、受控证据区 | request ID、时间、决定、阶段、策略版本 |

完整 Prompt、模型响应、文档正文或工具返回原文只在确有取证需要时进入访问受控的证据区；普通日志优先保存关联 ID、决定元数据、参数键/哈希和证据引用。

## 5. 三个关键判断

### 哪些风险需要模型外控制？

模型输出层可以观察到格式破坏、危险内容、引用缺失、敏感字段暴露或渲染风险。但身份伪造、对象级越权、租户隔离、工具副作用和资源耗尽，必须由应用或平台的确定性控制阻止或限制。输出审查不能证明上游没有越权读取，也不能撤销已经发生的副作用。

### 为什么 Prompt Injection、RAG、Agent 和输出安全会跨层？

Prompt Injection 可能从使用层输入或外部文档进入，在应用层影响上下文和流程，并进一步借助平台工具能力产生影响。RAG 由应用层编排，依赖平台索引/存储和身份范围，检索内容还会进入模型上下文。Agent 的规划和路由属于应用层，模型与工具运行能力属于平台层，授权和执行出口横跨两层。输出安全从应用层解析/审查延伸到使用层展示，并依赖平台日志和数据保护。

### 模型输出正常但鉴权缺失，是否安全？

不安全。服务端鉴权缺失时，形式正常或内容无害的输出仍可能基于越权读取的数据生成，也可能被后续组件用于越权动作。模型文本不能替代身份、对象权限和业务规则检查。

## 6. 示例：visitor 查询他人订单

用户是 `visitor`，通过聊天输入要求 Agent 查询另一客户的订单；模型生成合法 JSON，工具参数也符合 Schema。

1. 应用层策略引擎根据服务端会话、角色、租户、对象归属和业务规则拒绝请求。
2. 平台层工具网关、IAM 和业务订单 API 再次强制执行授权。
3. 使用层可以隐藏按钮或展示拒绝提示，但不能承担安全授权职责。
4. 拒绝前验证主体身份、会话有效性、角色、租户/数据范围、工具权限、目标对象归属、字段范围、参数组合和必要的同意或代理依据。
5. 审计记录保存请求 ID、时间、主体/会话引用、策略版本、工具与参数摘要、授权决定、拒绝阶段、原因码、结果和告警状态；敏感原文进入受控证据区。

合法 JSON 只证明字段、类型和格式符合工具契约，不证明身份有效、对象属于当前主体、角色有权访问或业务规则允许操作。
